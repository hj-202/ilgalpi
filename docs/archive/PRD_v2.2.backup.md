## 0. 문서 사용법과 변경 이력

### 0.1 우선순위 규칙

1. 이 문서의 본문은 v2.2 기준으로 정리되어 있다. 이전 버전의 "⚠ 표시 / 이 절이 우선" 방식의 덧붙임은 모두 본문에 흡수했다.
2. 사용자가 확정하지 않은 세부 사항은 §19 **미확정·확인 필요 항목**에 모아 두었고, 본문에서는 `[미확정]`으로 표시했다. 구현자는 이 항목을 임의로 확정하지 않고 사용자에게 확인한다.
3. 기존 `PRD.md`(v1)의 API 검증·오류 처리·보안 세부 정책은 이 문서와 충돌하지 않는 한 유지한다(§7.1).

## 1. 제품 정의와 핵심 UX

### 1.1 정의

- 서비스명: **일갈피(ILGALPI)**. 워드마크는 `일갈피.`(마지막 마침표는 브랜드 레드).
- 해야 할 일을 정리하고, 중요도·실제 마감·예상 소요시간·**선택한 날의 작업 가능한 총시간**을 고려해 **지금 무엇부터 실행하는 것이 좋은지 판단하도록 돕는 AI 기반 우선순위 의사결정 서비스**.
- 핵심 가치: 실행 순서를 결정하는 데 드는 시간을 줄인다. 단순한 할 일 저장·일정 관리가 아니다.
- 분석 핵심 기준은 **마감 시점(날짜·선택적 시각), 중요도, 예상 소요시간**이며, **작업 가능한 총시간은 우선순위 기준이 아니라 참고 제약 조건**이다. 단순 마감순 정렬이나 짧은 일 몰아주기가 아니라 통합 비교와 납득할 수 있는 이유를 제공한다.
- 복잡한 프로젝트 관리, 자동 시간표, 게임화 중심 앱으로 확장하지 않는다.

### 1.2 핵심 사용자 흐름

`(첫 방문) 온보딩 4장 → (후속) 로그인 선택` → `주간 캘린더에서 날짜 확인` → `할 일 빠른 입력` → `조건 설정` → `이날 작업 가능한 시간 설정` → `우선순위 추천받기` → `추천 결과 화면에서 순서·이유 확인` → `완료 체크` → `캘린더 완료 현황·전체 완료 스탬프` → `내 기록에서 평균 완료율·그래프 확인`

핵심 가치:

- 할 일이 많을 때 실행 순서를 결정하도록 지원
- 사용 가능한 시간과 작업 조건을 고려한 현실적인 추천
- 추천 결과에 대한 납득 가능한 이유
- 사용자 스스로 실행하고 완료 여부를 기록
- 축적한 기록으로 실행 현황·평균 완료율 확인

**온보딩의 예시 데이터는 실제 사용자의 할 일로 저장되면 안 된다.**

### 1.3 우선순위 구분

| 구분 | 내용 |
|---|---|
| **P0 — 핵심 안정화** | 현재 코드·기능 상태 파악, 데이터 보존·마이그레이션 확인, 할 일 등록·수정·삭제·완료, 선택 날짜별 캘린더, 실제 마감 정책, 우선순위 추천, Gemini 및 fallback 안정화, 완료율·기록 일관성, API 키 보안, 배포 전 필수 빌드 안정성 |

## 2. 정보구조와 내비게이션

### 2.1 하단 탭 (2개)

1. **홈** — 주간·월간 캘린더, 선택 날짜의 할 일, 할 일 추가·조건 설정, 이날 작업 가능한 시간, 우선순위 추천 결과, 완료 처리·진행 현황
2. **내 기록** — 평균 완료율 등 핵심 지표, 주간·월간 완료율 그래프, 지난 실행 기록, 실행 기록 전체보기, 비회원 로그인 안내·계정 상태, 의견 보내기

아이콘과 텍스트를 함께 표시하고 활성 탭은 브랜드 레드로 강조한다. 내 기록 탭 아이콘은 사람(User) 모양이 아니라 기록·통계를 연상시키는 형태로 한다 `[미확정: 아이콘 도안]`.

### 2.2 제거할 구조와 호환성

- 제거: `마이` 탭, `전체 할 일` 탭, `보관소`, `리포트` 탭, `마이 > 프로젝트 관리`.
- **UI 제거와 데이터 삭제는 별개다.** `Project` 타입, `Task.projectId`, `projects` 저장 배열, AI 요청/응답의 `projects`·`projectRankings`, 기본 추천의 프로젝트 순위 로직, v1·v2 마이그레이션은 삭제하지 않는다.
- 신규 프로젝트 생성·이름 수정·삭제 UI는 제공하지 않는다. 이미 프로젝트가 있는 기존 사용자에 대해 프로젝트 소속 표기·`프로젝트별 우선순위` 노출을 유지할지는 `[미확정]`(§19-5). 확정 전에는 기존 데이터에 영향이 없도록 읽기 전용으로만 유지한다.

### 2.3 화면 구성

- **온보딩**(첫 방문 오버레이/화면) → **로그인 선택**(후속, §11.2) → **홈** / **내 기록** / **지난 실행 기록 전체보기**(독립 페이지, §9.5).
- 조건 아코디언, 마감 시각 시트, 추천 결과, 의견 보내기 시트는 별도 페이지 수에 포함하지 않는다. 단, 추천 결과는 홈 내 같은 위치의 화면 전환이다(§4.2).
- 모바일 웹이 기본. 폭 320·360·390·428px에서 검증하고, 데스크톱에서는 가운데 최대 430~480px의 모바일형 캔버스를 보여준다. 데스크톱 2단 대시보드로 늘리지 않는다. 가로 스크롤이 없어야 한다. 실제 웹앱에 가짜 OS 상태바를 넣지 않는다.

## 3. 홈 화면

### 3.1 헤더

- 텍스트 워드마크 `일갈피.`, 서브카피 `복잡한 하루 속, 지금 해야 할 일부터`.
- 제목마다 "AI"를 반복하지 않는다. 기술 이름보다 사용자 행동·결과를 강조한다.

### 3.2 캘린더

**기본 동작**

- 주간 캘린더가 기본, 월간 전환 가능. **월요일 시작**.
- 최초 선택일은 사용자 로컬 기준 오늘. 날짜 탭 시 해당 날짜의 할 일을 표시한다. 오늘 아닌 날짜를 선택해도 실제 오늘과 구분된다(오늘은 굵은 글씨).
- 연월 제목, 이전/다음 이동, `[주간 | 월간]` 전환. 좌우 스와이프는 달력 영역 안으로 제한한다.

**날짜 선택 디자인**

- 선택 날짜 숫자를 **브랜드 레드 원형 Fill + 흰 숫자**로 강조한다.
- 요일·날짜·완료 현황 전체를 큰 카드로 감싸지 않는다. 비선택 날짜에는 불필요한 배경을 쓰지 않는다. 월간 칸 배경 없음.

**날짜별 완료 수 표시**

- 할 일이 있는 날짜 아래에 `완료 수/전체 수`(`0/4`, `2/4`, `3/4`)를 표시한다.
- 할 일이 없는 날짜에는 `—`, `0/0`, 장식용 점을 표시하지 않는다(빈칸).
- 글자 크기는 12px 이상으로 한다(§14.4).

**전체 완료 스탬프**

- 해당 날짜의 할 일이 1개 이상이고 모두 완료한 경우 완료 수 대신 스탬프를 표시한다. **브랜드 레드 원형 Fill + 내부 흰색 오각 별**, 꼭짓점은 살짝 부드럽게, 별 크기는 원 지름의 약 58~62%. 주간·월간·내 기록이 같은 SVG 컴포넌트를 사용한다.
- 톱니형 배지, 체크 배지, 표정 아이콘은 사용하지 않는다. 별 스탬프를 브랜드 앱 아이콘으로 자동 전용하지 않는다(§15).

날짜별 완료 수와 스탬프는 저장된 작업에서 매번 계산하며 별도 수치를 저장하지 않는다.

### 3.3 날짜별 실행 기록 영역

- 섹션 제목: 선택일이 오늘이면 `오늘의 실행 기록`, 아니면 `10월 22일의 할 일`처럼 날짜를 명시한다. 오늘이 아닌 날을 선택했는데 "오늘"이라고 쓰지 않는다.
- `완료 n/m`과 얇은 진행 바. **완료율 = 선택일에 계획된 작업 중 완료 수 ÷ 그날 계획된 작업 수**. 작업이 0개면 0%가 아니라 기록 없음.
- 모두 완료하면 짧은 긍정 메시지와 캘린더 스탬프. 연속 기록·벌점 등 압박 요소는 두지 않는다.

### 3.4 빠른 입력

- 선택 날짜를 기준으로 인라인 입력, Enter로 추가, 연속 등록 지원. 신규 할 일은 선택 날짜(`plannedDate`)에 저장된다.
- 기본값: 중요도 **보통** / 예상 소요시간 **미정** / 실제 마감 **없음** / 미완료.
- 제목은 trim 후 1~100자.
- 기존 자연어 입력 분리 기능이 유효하게 구현되어 있다면 호환성을 검토해 유지한다. (현재 코드에는 해당 기능이 없다 — §20.)
- 입력 영역 안내 문구와 placeholder: `예: 포트폴리오 수정하기`.

### 3.5 할 일 목록과 조건 설정 아코디언

**기본 목록**: 카드 반복이 아니라 **구분선 중심의 간결한 리스트**.

- 구성: 완료 체크 / 할 일 제목 / 조건 요약 칩 / `조건 설정` ↔ `조건 닫기` / 삭제 X 아이콘(중립색).
- 삭제에는 확인 절차를 둔다. 완료는 체크 해제로 취소 가능.
- 드래그 핸들은 실제 순서 변경이 지원될 때만 표시한다. 일반 목록은 등록순을 유지하고, 우선순위 정렬은 추천 결과에서만 적용한다.
- 오늘이 아닌 날짜의 목록, 완료 항목(취소선)도 동일한 리스트 규칙을 따른다.

**조건 설정 아코디언**(기본 닫힘, 항목 아래에 펼침, 연그레이 패널)

| 항목 | 선택지 |
|---|---|
| 할 일(제목 수정) | 텍스트 |
| 중요도 | 낮음 / 보통 / 높음 (이 순서) |
| 예상 소요시간 | 30분 이내 / 1시간 내외 / 2시간 이상 / 미정 |
| 실제 마감(선택) | 날짜, 시각 |

- **계획 날짜는 캘린더에서 결정하므로 아코디언 안에서 중복 설정하지 않는다.**
- 예상 소요시간은 대략적인 작업 규모(`effort`)다. 분 단위 입력은 없다. 개별 할 일의 `30분 이내`는 유지한다(작업 가능 시간의 `30분` 선택지 제거와 무관).
- 한 번에 하나만 열지 여러 개를 열지는 일관되게 유지하면 된다(현재: 하나만).
- 설정 즉시 목록의 칩을 갱신하고 저장한다.

### 3.6 칩 디자인

**조건 선택 칩(입력 컨트롤)**

- pill(999px), 비선택 = 화이트 + 연회색 1px 테두리, 선택 = 차콜/블랙 Fill + 흰 텍스트.
- 텍스트 내용에 맞는 너비, **좌우 패딩 약 14px**, 상하 패딩은 v2.1의 4px 유지 `[미확정: 터치 영역 확보 방식]`, 칩 간격은 v2.1의 4px 유지, Flex Wrap으로 자연스럽게 줄바꿈.
- **작업 가능 시간 칩과 높이·패딩·radius를 통일**하고 같은 컴포넌트를 사용한다.
- 실제 탭 영역은 시각적 칩 크기보다 충분히 크게 한다(최소 약 44px 높이 목표).

**조건 요약 칩(읽기 전용)**

- 일반 리스트: 연회색 Fill + 진한 회색 텍스트.
- 추천 결과: **화이트 Fill + 연한 테두리**(연핑크 배경에서 묻히지 않도록).
- 충분한 텍스트 대비. 칩을 불필요하게 크게 만들지 않는다. 글자 크기 12~13px.
- 표시 내용: 중요도 / 작업 규모(미정이면 `시간 미정`) / 마감(있을 때만).

### 3.7 이날 작업 가능한 시간

각 할 일의 예상 소요시간이 아니라 **사용자가 선택한 날짜에 작업할 수 있는 총시간**을 설정한다. 날짜별로 독립 저장한다.

섹션명: **`이날 작업 가능한 시간`**. 안내 문구(한 줄): `선택한 날의 총시간 · 할 일별 소요시간과 별개`.

**선택지(최종, 7개)**

| 순서 | 라벨 | 저장 값(분) |
|---|---|---|
| 1 | `1시간 이내` | 60 |
| 2 | `2시간` | 120 |
| 3 | `3시간` | 180 |
| 4 | `4시간` | 240 |
| 5 | `5시간` | 300 |
| 6 | `6시간` (정확히 6시간, `6시간 이상` 아님) | 360 |
| 7 | `직접 설정` | 5~1440 사이 정수 |

- 기존의 `30분`, `1시간` 빠른 선택은 제거하고 `1시간 이내`로 통합한다.
- **`1시간 이내`의 의미**: 그날 쓸 수 있는 총시간의 상한이 1시간이라는 선택지다. 저장 값은 60분이며 AI 요청의 `availableMinutes: 60`은 "총 60분 이하"로 해석한다(프롬프트·기본 추천·화면 라벨을 이에 맞춘다). 직접 설정에서 60분을 입력하면 같은 값이므로 `1시간 이내` 칩이 선택된 것으로 표시한다.
- **기존 저장 값 보존**: 이미 `dailyAvailableMinutes`에 30분 등 프리셋에 없는 값이 저장되어 있으면 삭제·변환하지 않고 `직접 설정: 30분`처럼 표시한다.
- 새 날짜의 기본값은 `preferences.availableMinutes`(기본 120분 = `2시간`)이며, 화면에 보이는 값과 AI에 보내는 값은 정확히 일치해야 한다.

**직접 설정**: 시·분 입력, 분 단위 정수 저장(7시간, 8시간, 7시간 30분 등). 검증: 시간·분은 정수, 분 0~59, 합계 5분 이상 24시간 이하. 잘못된 값은 저장하지 않고 이유를 알린다. 해당 날짜에만 독립 저장.

**칩 배치**

- 고정 3열 그리드 금지. 텍스트 너비의 칩을 Flex Wrap으로 배치하고, 줄바꿈은 화면 너비에 따라 달라질 수 있다. 특정 열 수를 강제하지 않는다.
- 마지막 줄에 칩 하나만 고립되는 배치를 가능한 한 방지한다(예: 균형 줄바꿈 처리). 320·360·390·428px에서 검증한다.
- 선택 상태는 차콜 Fill + 흰 텍스트. 조건 설정 칩과 동일한 디자인 시스템.

## 4. 우선순위 추천

### 4.1 CTA

- 최초: **`우선순위 추천받기`**. 이미 추천 결과가 있고 조건 변경으로 재추천이 필요하면: **`다시 추천받기`**.
- `AI 추천`과 `기본 추천` 버튼을 나누지 않는다. 별도의 `AI 없이 기본 추천 보기` 링크도 두지 않는다.
- 미완료 할 일이 없으면 CTA 비활성 + 안내(`먼저 할 일을 추가해 주세요` 또는 `이날 할 일을 모두 마쳤어요`). 로딩 중 중복 클릭을 막는다.
- 작은 고지: `추천 시 할 일과 조건이 Google Gemini로 전송됩니다.`
- 작업이 30개를 초과하면 AI 분석 한도를 안내한다(§7.1).

### 4.2 결과 화면 전환 — 기본 목록을 대체

- **추천 결과는 기본 할 일 목록을 대체해 같은 위치에 표시한다.** 목록 아래에 추천 패널을 추가해 같은 할 일이 두 번 나타나지 않게 한다.
- 결과 화면 구성: `← 할 일 목록으로` / 제목 / 추천 방식 표기 / 추천 우선순위 리스트 / 각 항목 완료 체크 / 필요 시 재추천 CTA.
- 제목: 오늘이면 `오늘의 우선순위`, 다른 날짜면 `10월 22일의 우선순위`.
- 기본 목록으로 돌아가도 기존 조건·입력 상태를 유지한다.
- 기존 추천 결과가 있을 때 결과 화면으로 다시 들어가는 진입점과 앱 재방문 시 기본 노출 화면은 `[미확정]`(§19-1).

### 4.3 추천 대상과 판단 기준

- 대상: **선택 날짜에 계획된 모든 미완료 작업**. 상위 3개 제한 없음. 소요시간이 작업 가능 시간을 초과해도 순위에서 제외하지 않는다. 결과는 날짜별로 관리한다.
- 판단 기준: 중요도, 실제 마감일·마감 시각, 예상 소요시간(규모), 선택 날짜의 작업 가능 총시간(참고 제약), v1에서 유지하기로 한 유효 조건.
- **마감 임박도는 항상 실제 오늘·현재 시각 기준**으로 계산하고, 계획 날짜(선택일)와 구분한다. 과거·미래 날짜를 추천해도 마감까지 남은 시간을 선택일 기준으로 계산하지 않는다.
- 피로도·장소·감정 등 추가 가중치는 사용하지 않는다.
- 추천을 생성해도 `plannedDate`를 조용히 바꾸지 않는다.

### 4.4 추천 방식과 오류·fallback

- 하이브리드: Gemini 호출이 **실제로 성공하면 AI 분석 사용**, 호출이 실패하면 **조건 기반 추천으로 안전하게 전환**한다. 오류 분류(§7.3)에 따라 원인과 조치를 안내하고, API 실패가 핵심 기능 전체를 막지 않는다.
- 표기: 실제 Gemini 호출이 성공한 결과만 `AI 추천`. 규칙 기반은 `기본 추천 · AI 분석 아님`. 실제 AI 호출 없이 만든 결과를 AI가 분석했다고 표시하지 않는다.
- 전환 시 사용자 안내 방식(자동 전환 후 한 줄 안내 + `다시 시도` 등)의 세부는 구현 시 제안하고 사용자가 확인한다 `[미확정]`(§19-2).
- 입력되지 않은 날짜·시각·소요시간을 임의로 생성하지 않는다.

### 4.5 추천 리스트 디자인

- **아주 연한 핑크 배경의 단일 리스트 영역**. 개별 카드 중첩 금지.
- 각 행: 순위 원 / 할 일 제목 / 완료 체크 / 조건 요약 칩(화이트 Fill + 연한 테두리) / 추천 이유.
- 설명 문장은 한 번만 쓰고 생성 시각은 표시하지 않는다. 분홍 안내 카드를 반복하지 않으며, 재추천 필요는 한 줄 텍스트로 알린다.

**순위 원**

| 순위 | 스타일 |
|---|---|
| 1순위 | 브랜드 레드 Fill `#F44D52` + 흰 숫자 |
| 2순위 | 1순위보다 밝고 부드러운 레드·핑크 Fill + 충분한 대비의 진한 숫자. 탁하거나 어두워 보이지 않게 조정 `[미확정: 색상값]` |
| 그 외 | 중립 회색이 아닌 **아주 연한 핑크 Fill + 진한 레드 계열 숫자**. 연핑크 배경에서 구분되도록 대비 확보, 비활성처럼 보이지 않게 |
| 3순위 추가 강조 | 추천 점수 차이가 가까울 때만 가능. **현재 추천 결과에는 점수가 없고 AI가 점수를 만들면 안 되므로**(§7.2) 정의가 필요하다 `[미확정]`(§19-3). 확정 전에는 1·2순위에만 위계를 둔다 |
| 완료 항목 | 기존 순위 숫자를 유지하고 제목 취소선·체크 상태 반영. 원 색상은 v2.1의 뉴트럴 유지 `[미확정: 연핑크 배경에서의 가독성 확인]` |

### 4.6 추천 이유

태그를 반복하는 문장이 아니라 **왜 이 작업을 지금 시작하거나 먼저 처리하면 좋은지** 설명한다.

- 나쁜 예: `중요도 높음 · 마감 내일`, `입력 조건을 기준으로 추천`, `예상 소요시간 30분`.
- 권장 예(실제 입력 조건에 근거가 있을 때만 사용):
  - `마감이 가까워요. 먼저 마치면 다른 작업을 더 여유 있게 진행할 수 있어요.`
  - `지금 확보한 시간 안에서 처리할 수 있어 먼저 끝내두기 좋아요.`
  - `긴 작업 사이 짧게 처리하면 흐름을 끊지 않고 마무리할 수 있어요.`
  - `시간이 오래 걸리는 작업이라 먼저 시작해 부담을 나눠보세요.`
- 원칙: 항목당 1~2문장, 모바일에서 2줄 내외, 태그와 중복 설명 지양, 행동에 도움이 되는 이유, **근거 없는 비교·마감·시간 창작 금지**. 한 예시 문장이 다른 작업의 존재나 시간 합계를 전제로 한다면 그 전제가 입력에서 확인될 때만 쓴다.
- AI 프롬프트와 기본 추천(규칙 기반)의 이유 문장을 모두 이 원칙으로 맞춘다. 규칙 기반 보조 설명: `마감·중요도·소요시간을 기준으로 실행 순서를 정리했어요.`

### 4.7 완료와 재추천

- 추천 결과에서 완료 체크 가능. 완료한 항목은 **즉시 삭제하지 않고** 기존 순위를 유지하며 취소선·체크 상태를 반영한다. 완료 상태는 기본 목록·캘린더·내 기록에 동기화된다.
- **완료·완료 취소만으로 AI를 다시 호출하지 않는다**(stale이 아님).
- 재추천 필요(stale)가 되는 경우: 해당 날짜의 할 일 추가·삭제·이동, 제목·프로젝트·마감일·마감 시각·중요도·소요시간 변경, 해당 날짜의 작업 가능 시간 변경, 실제 오늘 날짜 변경으로 기존 판단이 유효하지 않게 된 경우.
- 추천 전에 이미 완료한 작업은 완료 기록에 남고 새 추천 대상에서 제외된다.

## 5. 날짜·마감 정책

### 5.1 두 날짜의 차이

| 필드 | 의미 | 사용처 |
|---|---|---|
| `plannedDate` | 사용자가 **그날 하려고 등록한 날** (캘린더에서 선택한 날짜) | 캘린더 `n/m`, 날짜별 목록, 완료 스탬프, 통계 집계 |
| `dueDate` | 작업을 마쳐야 하는 마지막 날짜(선택) | 우선순위 판단, 마감 칩 |
| `dueTime` | 마감 날짜에 붙는 정확한 시각(선택, `HH:mm`) | 시각 임박 판단, 마감 칩 |
| `completedAt` | 완료를 누른 시각 | 완료 상태 복원 |

- `plannedDate`와 `dueDate`/`dueTime`은 독립이다. 마감을 바꿔도 계획 날짜가 자동 이동하지 않고, 계획 날짜를 옮겨도 마감이 바뀌지 않는다.
- 미완료 할 일의 **자동 이월은 금지**한다(§8).
- 예: 10/20에 `지원서 작성`을 계획하고 10/21 18:00 마감을 설정하면 10/20 목록에 보이고, 10/20 기준 칩은 `내일 18:00`.

### 5.2 마감 칩 표기

24시간제 `HH:mm`. 요일은 축약하지 않고 `금요일`로 쓴다.

| 상황 | 표시 |
|---|---|
| 오늘 18:00 | `오늘 18:00` |
| 내일 18:00 | `내일 18:00` |
| 이번 주 안(오늘·내일 이후) | `금요일` / `금요일 18:00` |
| 다음 주 | `다음 주 금요일` / `다음 주 금요일 18:00` |
| 2주 이상 먼 날짜 | `11월 6일` / `11월 6일 18:00` |
| 시각 없음 | 날짜 부분만 (`오늘`, `내일`, `금요일`) |
| 이미 지남 | `마감 지남` |
| 마감 없음 | **칩 숨김** |

- `10/21 18:00` 형태나 `D-3`, `오후 6시`, `낮 12시`는 쓰지 않는다. 2주 이상 등 상대 표기가 혼란을 줄 수 있으면 월·일을 사용한다.
- 상세(조건 패널)에서는 실제 `YYYY.MM.DD` 값을 정확히 보여 준다.
- `오전 12시`는 `00:00`, `오후 12시`는 `12:00`으로 저장한다.

### 5.3 마감 날짜·시각 선택

- 마감일(선택): 날짜 선택기. 과거 날짜는 저장 가능하되 `이미 지난 날짜예요` 안내.
- 마감 시각(선택): **날짜가 있을 때만** 활성화. 날짜 없이 시각만 저장되지 않는다. 탭하면 바텀시트(`마감 시각 선택`)를 연다.
- 오전/오후·시·분 **휠 3열**(분은 1분 단위, 가운데 강조·스냅, 방향키 지원)을 우선 지향한다. 빠른 선택 칩은 두지 않는다. 휠이 불안정하면 접근성과 정확한 입력이 가능한 대안을 쓸 수 있고, **정확히 작동하는 것이 시각적 휠 흉내보다 우선**이다.
- 버튼: `시각 없음`(dueTime=null) / `적용하기`(레드). 닫기·배경 탭은 취소(기존 설정 유지). 저장 값은 24시간제 `HH:mm`.

## 6. 데이터·저장·마이그레이션

### 6.1 작업 필드

| 필드 | 규칙 |
|---|---|
| `id` | UUID |
| `title` | 필수, trim 1~100자 |
| `plannedDate` | 필수, 로컬 `YYYY-MM-DD`, 등록 시 선택 중인 날짜 |
| `projectId` | `null` 또는 기존 프로젝트 ID(UI 정책은 §2.2) |
| `importance` | `low`/`medium`/`high`, 기본 `medium` |
| `effort` | `short`(30분 이내)/`medium`(1시간 내외)/`long`(2시간 이상)/`null`(미정) |
| `legacyMinutes` | 이전 분 단위 값. **보존만** 하며 화면·분석에 쓰지 않음 |
| `dueDate`, `dueTime` | 선택. `dueTime`은 `dueDate` 없이 불가 |
| `isCompleted`, `completedAt` | 완료 시 ISO, 취소 시 `null` |
| `createdAt`, `updatedAt` | ISO |

`effort`를 분으로 환산하거나 합산하지 않는다. `2시간 이상`·`미정`은 규모·불확실성으로만 해석한다.

### 6.2 저장 구조 `ilgalpi:v3`

- `projects`, `tasks`, `preferences.availableMinutes`, `dailyAvailableMinutes{YYYY-MM-DD: 분}`, `recommendations{YYYY-MM-DD: StoredRecommendation}`.
- 날짜별 `completed/total`, 스탬프, 통계는 **저장된 작업에서 매번 계산**하며 별도 수치를 저장하지 않는다(어긋남 방지). 과거 기록이 수정되면 통계가 자동으로 일관되게 재계산된다.
- 온보딩 완료는 `ilgalpi:onboarded`로 로그인 여부와 별개로 관리한다.
- 비회원 데이터는 브라우저 localStorage에 저장한다. 시크릿 모드, 사이트 데이터 삭제, 기기 변경으로 데이터가 사라질 수 있음을 안내한다(내 기록 로그인 안내 카드, 저장 불가 시 상단 안내).

### 6.3 마이그레이션 (유지)

- **v1 → v2 → v3**를 순서대로 연쇄 변환한다. 변환·저장 검증 전에는 이전 키를 삭제하지 않는다.
- `ilgalpi:v1`, `ilgalpi:v2` 원본은 **삭제하지 않는다.** v3가 손상되면 `ilgalpi:v3:corrupt-backup`에 원본을 보관한다. 임의로 저장 키를 삭제하거나 데이터를 초기화하지 않는다.
- v1 → v2: 레거시 미완료 작업의 `plannedDate`는 마이그레이션 당일. 완료 작업은 `completedAt` 로컬 날짜 → `createdAt` → 마이그레이션 당일 순으로 배치(추정값일 수 있음을 안내). 기존 `dueDate` 유지, `dueTime=null`.
- v2 → v3: 분 → 규모 매핑 `≤30분 → 30분 이내`, `31~90분 → 1시간 내외`, `91분 이상 → 2시간 이상`, `null → 미정`. 원래 분 값은 `legacyMinutes`에 보존. 이전 단일 추천 결과는 최신이 아니므로 폐기하고 재추천을 유도.
- **v2.2에서 스키마 변경은 필요 없다.** 작업 가능 시간 프리셋 변경은 UI 상수의 변경이며 저장 값(분)은 호환된다. 이후 구현에서 필드를 추가하면 v3 안에서 호환되는 선택 필드로 추가하거나 v4 마이그레이션을 별도로 정의한다 `[미확정]`.
- 로그인 도입 시 로컬 데이터 이전 정책은 §11.4.

## 7. 추천 엔진·API

### 7.1 유지 항목 (v1 §7·§8, 충돌 없는 부분)

`/api/recommend`, Gemini 서버 호출, 환경변수, UUID → 축약 ID 매핑, 순위/ID 유효성 검증(누락·중복·존재하지 않는 ID·연속 rank), 구조화 출력 검증 후 최대 1회 재시도, 타임아웃·오류 처리, 규칙 기반 기본 추천, AI와 기본 추천 구분, 로컬 타임존/날짜 기반 판단, stale 판정(완료만으로는 stale 아님), 작업 30개 초과 시 AI 한도 안내. **`focusPlan`과 Focus 관련 검증(3개 이하·시간 합 ≤ 가용 시간)은 폐기.**

### 7.2 요청·응답 스키마

- **요청**: `currentDate`(실제 오늘), `planDate`(추천 대상 날짜), `currentTime`, `timezone`, `availableMinutes`(planDate의 작업 가능 시간), `projects`, `tasks[{id, projectId, title, dueDate, dueTime, importance, effort}]`. `effort ∈ {short, medium, long, null}`. 분 단위 소요시간은 보내지 않는다.
- **응답**: `projectRankings`, `taskRankings`, `warnings`. 점수 필드는 없다. AI가 근거 없는 점수·수치를 만들지 않는다.
- 시각이 있는 오늘 마감은 현재 시각과 시간대로 남은 분(`minutesUntilDue`)을 판단한다. 서버 로컬/UTC를 사용자 시각과 혼동하지 않는다.
- **근거 검사**: 이유·주의사항에 입력에 없는 날짜(`M월 D일`, `M/D`), 시각(`HH:mm`), 지속시간(`N분`, `N시간`)이 있으면 위반으로 보고 1회 재시도하며, 계속 위반하면 결과를 표시하지 않는다. 허용 값은 입력의 마감일·마감 시각·계획일·오늘, 작업 규모 라벨, 작업 가능 시간, 마감까지 남은 시간.
- **이유 품질**: §4.6 원칙을 프롬프트에 반영하고, 태그 나열형 문장을 금지한다.
- `1시간 이내`(=60분)의 상한 의미를 프롬프트의 `availableMinutes` 설명에 반영한다(§3.7).

### 7.3 오류 분류

`MISSING_API_KEY`(키 없음), `AI_AUTH_ERROR`(401/403·"API key not valid"), `AI_MODEL_ERROR`(404 등 모델 오류), `AI_RATE_LIMITED`(사용량 제한), `AI_TIMEOUT`, `AI_UPSTREAM_ERROR`, `AI_INVALID_RESPONSE`(형식·근거 검사 실패), `NETWORK_ERROR`, 입력 오류(`INVALID_REQUEST`, `NO_TASKS`, `TOO_MANY_TASKS`). 원인과 조치를 구분해 안내한다. 모델이 `thinkingLevel` 설정을 거부하면 설정 없이 1회 재호출한다. 지원 여부를 확인하지 않은 Gemini 모델명을 임의로 사용하지 않는다.

### 7.4 진단

`npm run check:gemini`는 키·모델·엔드포인트·요청 형식을 Gemini에 직접 확인하고, 개발 서버가 있으면 `/api/recommend` 전체 경로까지 확인한다. 키 값은 출력하지 않는다. **실제 호출 성공을 확인하기 전에는 AI 추천 완료로 보고하지 않는다.**

## 8. 완료 기록과 선택형 이월

- 완료 및 완료 취소 가능. 완료 상태는 저장 데이터에 반영된다.
- 미완료 항목의 자동 이월 금지. 날짜별 목록의 `미완료 옮기기` → 옮길 작업 직접 선택 → `다음 날로 이동`(선택일이 오늘이 아니면 `오늘로 이동`도 제공).
- **미완료 작업만** `plannedDate`를 바꿔 이동한다(복제 없음). 실제 마감(`dueDate`·`dueTime`)은 유지한다.
- 완료된 작업은 원래 날짜에 남아 원래 날짜의 완료 기록은 바뀌지 않는다. 한 작업은 한 날짜에만 집계되므로 통계에 중복 집계되지 않는다.
- 이월은 관련 날짜들의 추천을 재추천 필요 상태로 만든다.
- 늦게 완료한 작업도 **원래 계획한 날짜**의 완료로 집계한다(실제 수행일 기준 분석은 후속 후보).

## 9. 내 기록

하단 탭 이름은 **내 기록**. 화면 순서:

1. `내 기록` 제목
2. 핵심 통계 3개
3. 로그인 안내 또는 계정 정보
4. `얼마나 해냈을까?` 그래프
5. `지난 실행 기록` 최근 3개 + `전체보기 ›`
6. `의견 보내기 ›` (하단 오른쪽)

`사용법 다시 보기`는 이 화면에서 제거한다. 비회원 상단 우측 사람 아이콘을 두지 않는다.

### 9.1 핵심 통계

모든 지표는 **그래프의 선택 조회 기간과 연동**된다(홈의 선택 날짜와는 독립). 집계 기준은 §8과 동일하게 `plannedDate`다.

| 지표 | 정의 |
|---|---|
| **평균 완료율** | 선택 기간에 할 일이 있는 날짜들의 **일별 완료율 산술평균**. 일별 완료율 = 그날 완료 수 ÷ 그날 전체 수. 할 일이 없는 날짜는 제외, 있지만 완료가 없으면 0%로 포함. 전체 합계 기준의 누적 완료율이 아니며, 월간 주차 막대의 평균도 아니다 |
| **완료한 일** | 선택 기간에 완료한 총 할 일 개수 `[미확정: 계획일 기준 vs 완료일 기준]`(§19-6) |
| **모두 완료한 날** | 할 일이 1개 이상이고 모두 완료한 날짜 수(캘린더 스탬프와 같은 기준) |

화면: 큰 숫자와 작은 라벨, 세 지표를 한눈에 비교, 과도한 카드 장식·그림자 지양. 기간에 기록이 없으면 평균 완료율을 임의 값(0%)으로 표시하지 않고 빈 상태 표시(`–`)로 둔다 `[미확정: 표시 형태]`.

### 9.2 그래프 `얼마나 해냈을까?`

**조회 모드**

- **주간**: 월~일 7개 막대, 각 날짜 완료율.
- **월간**: 해당 월을 월요일 기준 주차로 나눠 4~6개 막대. 해당 월의 날짜만 집계. 주차 완료율 = 그 주차의 완료 수 ÷ 그 주차 전체 할 일 수. (상단 평균 완료율은 이 막대의 평균이 아님.)
- 주간/월간 전환, 이전/다음 기간 이동, 현재 조회 기간 표시. 기간을 바꾸면 상단 지표도 바뀐다. 미래 기간으로의 이동 허용 여부는 `[미확정]`.

**디자인**

- 흰 배경, 둥근 단일 컨테이너, 연한 1px 테두리, 충분한 내부 여백. 타이틀 왼쪽·모드 전환 오른쪽, 기간 정보와 이전/다음 이동. 차트 아래 얇은 기준선, 연회색 요일·주차 라벨, 선택 항목 라벨은 레드. `막대를 눌러보세요` 안내는 두지 않는다.
- 막대: 기본 연코랄 `#F6B8BC`, 선택 `#F44D52`, 위쪽 라운드, 0~100% 척도. 월간 막대는 주간보다 넓게 배치할 수 있고 막대 간격은 일관되게 유지한다. 터치 영역은 막대 시각 크기보다 충분히 크게.
- **최초 선택**: 기간에 기록이 있으면 완료율이 가장 높은 항목. 동률이면 가장 최근 항목. 클릭하면 선택 변경, 선택 막대만 진한 레드.
- **할 일이 없는 날짜와 완료율 0%인 날짜를 구분한다.** (0% 막대·기록 없음의 시각 표현은 `[미확정]`.)

**툴팁**: 선택 막대 바로 위 작은 화이트 말풍선. 화이트 Fill, 레드 텍스트, 연한 1px 테두리, 미세한 그림자, 작은 삼각형 꼬리, `75%`·`100%`처럼 퍼센트만 표시, 약 64×32px, 주간·월간 동일 크기, 막대 위 중앙 정렬, 막대 높이에 따라 이동. 차트 헤더·화면 가장자리와 겹치지 않는다.

**하단 선택 항목 상세**

- 주간 예: `수요일 실행 기록` / `75% · 완료 3/4` / `계획한 4개의 할 일 중 3개를 완료했어요.`
- 월간 예: `4주차 실행 기록` / `80% · 완료 16/20`.
- 실제 선택 데이터에 따라 바꾼다.

**기록 없음**: Empty state(§10.4)를 보여주고 가짜 막대나 임의 완료율을 표시하지 않는다.

### 9.3 지난 실행 기록 (내 기록 화면)

- 섹션명 `지난 실행 기록`, 오른쪽 보조 액션 `전체보기 ›`(진한 그레이). `최근 날짜순` 문구는 없다.
- 최근 기록 **3개**: 날짜·요일 / 완료 수 / 전체 수 / 완료율 / 상세 이동. 선택하면 **홈의 해당 날짜로 이동**한다.
- 대상 범위(오늘까지만, 할 일 있는 날만 등)는 `[미확정]`(§19-7).

### 9.4 로그인 안내·계정 영역

- 비회원: 요약 지표 바로 아래 카드 — `지금은 이 기기에만 저장돼요` / `Google로 로그인하면 기록을 다른 기기에서도 이어볼 수 있어요.` / CTA `Google로 계속하기`. 스타일: 연한 레드 배경, 진한 텍스트, 브랜드 레드 Fill 버튼.
- 로그인 사용자: 같은 위치에 계정 정보와 **실제** 동기화 상태를 표시.
- 인증이 구현되기 전에는 CTA를 비활성 + `준비 중`으로 표시하며 로그인·동기화가 되는 것처럼 보이게 하지 않는다(§11.3).

### 9.5 지난 실행 기록 전체보기

- **모달이 아닌 독립 페이지**: 상단 뒤로가기 / `지난 실행 기록` 타이틀 / 날짜 최신순 / 누적된 전체 기록 / 세로 스크롤.
- 10개·12개 등 임의의 고정 총량 제한 금지. 데이터가 많으면 페이지네이션 또는 점진적 로딩 가능.
- 기록 선택 시 홈의 해당 날짜로 이동, 뒤로가기 시 내 기록으로 복귀(브라우저 뒤로가기와도 자연스럽게 동작해야 함 `[미확정: 라우트 vs 앱 내부 뷰 상태]`).

## 10. Empty State 및 기타 상태

### 10.1 공통 디자인

연핑크 Rounded Square 배경 1개 / 내부에 중복된 감싸기 면 없음 / 충분히 큰 Fill형 SVG 아이콘(배경 면에 비해 작아 보이지 않게) / 중앙 정렬 / 제목·설명·필요 시 CTA. 간격: 아이콘→제목 20~24px, 제목→설명 8~10px, 설명→CTA 20~24px.

### 10.2 상황별

| 상황 | 아이콘 | 제목 | 설명 | CTA |
|---|---|---|---|---|
| 홈 — 할 일 없음 | Fill 체크리스트/클립보드 | `아직 등록한 할 일이 없어요` | `오늘 해야 할 일을 하나씩 적어보세요.` (오늘이 아니면 표현 조정) | `+ 할 일 추가하기` 레드 Fill. 입력창이 이미 보이면 버튼 중복 대신 입력창 포커스로 연결 |
| 내 기록 — 기록 없음 | Fill 막대그래프 | `아직 쌓인 기록이 없어요` | `할 일을 완료하면 여기에 실행 기록이 쌓여요.` | `할 일 등록하러 가기` 화이트 Outline → 홈의 입력 영역으로 이동 |
| 추천할 미완료 없음 | Fill 완료/체크 | `추천할 할 일이 없어요` | `새로운 할 일을 추가하면 우선순위를 추천해 드릴게요.` | 없음 |
| 조회 기간 기록 없음 | Fill 막대그래프 | `이 기간에는 기록이 없어요` | `할 일을 완료하거나 다른 기간을 선택해 보세요.` | 없음 |

### 10.3 Empty state가 아닌 상태

로딩, 데이터 저장 실패, 추천 오류, 통계 조회 오류, 네트워크 오류는 Empty state와 구분한다. 실제 상황에 맞는 안내와 재시도를 제공한다.

### 10.4 선택 날짜만 비어 있을 때

다른 날짜에 등록된 할 일이 있어도 데이터는 숨기기만 하고 삭제하지 않는다. 날짜별로 `이 날짜에 계획된 할 일이 없어요.`를 쓸 수 있다(§10.2의 홈 Empty state 표현을 날짜에 맞게 조정).

## 11. 온보딩과 Google 로그인

### 11.1 온보딩 4장

**공통**: 최초 방문 시 노출, 좌우 스와이프, 현재 슬라이드 인디케이터(탭으로 이동 가능), `다음` / 우측 상단 `건너뛰기` / 마지막 `시작하기`, 재방문 시 반복 노출 금지. **예시 데이터는 화면 전용이며 저장소에 저장되지 않는다.** 375×667에서 스크롤 없이 CTA까지 보인다. 슬라이드는 컴포넌트로 분리해 추후 고품질 일러스트로 교체 가능하게 한다.

| # | 제목 | 설명 | 그래픽 |
|---|---|---|---|
| 1 | `할 일을 자유롭게 정리해요` | `생각나는 일을 적고, 필요한 조건만 간편하게 설정해요.` | 체크리스트, 할 일 입력, 조건 선택 |
| 2 | `무엇부터 할지 순서를 찾아요` | `마감과 중요도, 소요시간을 고려해 실행 순서를 추천해요.` | 순위 1·2·3, 할 일 리스트, 조건 칩, 간단한 추천 이유 |
| 3 | `완료한 만큼 기록해요` | `하루의 완료 현황을 확인하고, 다 마친 날에는 도장이 찍혀요.` | 주간 캘린더, `완료 수/전체 수`, 별 스탬프 |
| 4 | `나의 실행 패턴을 확인해요` | `쌓인 기록으로 내가 얼마나 해냈는지 살펴보세요.` | 간결한 막대그래프, 완료율, 실행 현황 |

**그래픽 스타일**: 2D 플랫, 화이트·연코랄·브랜드 레드, 단순한 면형 아이콘 또는 일갈피 UI에서 차용한 미니 그래픽. 복잡한 3D·캐릭터·과한 그라데이션 지양. 네 화면의 스타일을 통일한다. **최종 일러스트 도안은 미확정**이며 현재의 연한 코랄 그라데이션 영역(v2.1)을 유지할지는 §19-8에서 확인한다.

### 11.2 로그인 선택 화면 (온보딩 이후 별도 화면)

- 제목 `나의 실행 기록을 이어가요` / 설명 `계정에 기록을 보관하고 다른 기기에서도 이어서 사용해 보세요.`
- Primary `Google로 계속하기` / Secondary `로그인 없이 시작하기`.
- 로그인 없이도 핵심 기능을 모두 쓸 수 있다.
- **인증이 구현되기 전에 이 화면을 노출할지, 노출한다면 Primary 버튼을 어떻게 처리할지는 `[미확정]`**(§19-4). 제안: 인증 구현 전에는 이 화면을 생략하고 온보딩 후 바로 홈으로 진입한다(작동하지 않는 Primary 버튼을 두지 않기 위해).

### 11.3 비회원

할 일 등록, 조건 설정, 추천, 완료 체크, 내 기록·통계 확인, 브라우저 로컬 저장. 브라우저를 닫았다 열어도 유지된다. 시크릿 모드·저장 데이터 삭제·기기 변경에 따른 데이터 손실 가능성을 안내한다.

### 11.4 로그인 사용자 (P2, 미구현)

- 현재 프로젝트에는 인증·DB 구조가 없다. 구현 전까지 로그인·동기화가 정상 완료된 것처럼 표시하지 않는다.
- 구현 시 요구사항: 계정 기반 데이터 보관, 여러 기기 동기화, 기존 기록 복원, **로그인 전 로컬 데이터 이전**(id 기준 병합으로 중복·충돌·유실 방지), 로그아웃·재로그인·인증 실패 처리.
- OAuth·DB 비밀키는 서버 환경변수로만 보관하고, 계정별 접근 권한을 분리한다.
- 선결 결정(사용자): 인증/DB 제공자(예: Auth.js + Google OAuth + Postgres/Supabase, 또는 Firebase Auth + Firestore), Google Cloud OAuth 클라이언트 ID/Secret, DB 연결 정보.

## 12. 의견 보내기

- 진입: **내 기록 하단 오른쪽 `의견 보내기 ›`**. 비로그인 사용자도 이용 가능.
- UI: 바텀시트 또는 모달 우선 검토. 입력: 의견 유형(`불편한 점` / `기능 제안` / `기타`), 자유 의견, 이메일(선택).
- 전송: **실제 전송 경로가 있어야 한다. 미구현 상태에서 가짜 성공을 표시하지 않는다.** 전송 중 중복 제출 방지, 실패 시 입력 내용 유지·재시도 지원, 성공 시 짧은 토스트.
  - 성공: `의견이 전달되었어요.` / 실패: `전송하지 못했어요. 다시 시도해 주세요.`
- 전송 경로(이메일 서비스, 폼 서비스, DB 등)와 개인정보 안내는 `[미확정]`(§19-9). 경로가 정해지기 전에는 버튼을 비활성 또는 미노출로 둔다.
- **추천 결과 평가**(`이 추천이 도움이 되었나요?` — `도움됐어요` / `아쉬워요`)는 **후속(P2) 기능**이며 의견 보내기와 별개다.

## 13. 데이터 분석 (Mixpanel, P2)

정식 연동은 후속 단계. 검토 중인 핵심 이벤트: 서비스 방문, 온보딩 시작·완료/건너뛰기, 로그인/비회원 선택, 할 일 추가, 조건 설정, 작업 가능 시간 설정, 추천 요청, 추천 결과 노출, AI/조건 기반 추천 유형, 추천 이후 완료, 완료 체크/해제, 내 기록 진입, 주간·월간 전환, 그래프 막대 선택, 지난 실행 기록 전체보기, 의견 보내기, 추천 평가.

분석 목적: 할 일 등록 후 추천 전환율, 추천 확인 후 완료 전환율, 기능별 사용률, 재방문, 온보딩 이탈, 로그인 선택률, 추천 유용성.

원칙: 실제 발생한 이벤트만 기록, 중복 수집 방지, **할 일 제목·이메일 등 민감한 원문을 이벤트에 전송하지 않음**, 비회원 익명 식별과 로그인 후 연결 고려, Mixpanel을 원본 데이터 저장소로 쓰지 않음. 이 프로젝트에는 아직 연동 코드가 없다.

## 14. 디자인 시스템

### 14.1 방향

모바일 중심의 정돈된 생산성 서비스. 화이트 기반, 레드 포인트, 연코랄·연핑크 보조, 차콜 본문, 필요 시 연회색 구분선. 과도한 카드 중첩과 큰 카드 남발을 피한다. 채도가 낮고 탁한 레드는 쓰지 않는다.

### 14.2 컬러 토큰

`app/globals.css`의 `@theme` 토큰 **한 곳**에서만 관리한다. 브랜드 컬러 변경은 확정되지 않았으므로 `--color-primary: #F44D52`를 유지한다(비교 후보 `#FF3B50`, `#E82E45`는 이 값만 바꿔 비교).

| 토큰 | 값 | 용도 |
|---|---|---|
| `--color-primary` | `#F44D52` | CTA, 선택 날짜 원, 1순위 원, 스탬프, 진행 바, 활성 탭 |
| `--color-primary-dark` | `#E23C41` | hover, 경고 텍스트 |
| `--color-primary-soft` | `#FFF0F0` | 연핑크(추천 배경, Empty state, 로그인 카드 등 제한 영역) |
| `--color-ink` | `#19191B` | 본문 |
| `--color-subtle` | `#767780` | 보조 텍스트 |
| `--color-line` | `#E8E9ED` | 구분선·테두리 |
| `--color-chip` | `#F0F1F3` | 정보 칩 |
| `--color-selected` | `#242428` | 선택된 조건 옵션 |
| 막대 기본 | `#F6B8BC` | 그래프 비선택 막대 `[토큰화 필요]` |

### 14.3 컴포넌트 규칙

CTA = 레드 Fill / 선택 칩 = 차콜 Fill / 정보 칩 = 회색 또는 화이트+테두리 / 선택 날짜 = 레드 원 / 스탬프 = 레드 원 + 흰 별 / 추천 순위 = 강한 레드→연핑크. 레드를 조건 칩, 긴 설명, 모든 캘린더 날짜에 쓰지 않는다.

### 14.4 타이포그래피

주요 본문 14~16px, 보조 설명 12~14px, 작은 칩 12~13px. 제목은 명확한 위계. **10~11px 텍스트 남용 금지**. 충분한 명도 대비. 시스템 폰트 유지.

### 14.5 반응형·접근성

320·360·390·428px 검증, 데스크톱은 모바일 콘텐츠를 중앙 배치, 가로 스크롤 금지, 충분한 탭 영역, 키보드 접근성(탭 이동·Enter/Space·Escape, 방향키), 아이콘 버튼의 `aria-label`.

## 15. 파비콘·앱 아이콘 (교체 정책)

현재 서비스에 맞지 않는 기존 아이콘은 **교체 대상**이다. 이번 정책은 최종 브랜드 심볼의 확정이 아니라 **심플한 임시 아이콘 사용**이다.

- 브라우저 파비콘을 제공하고, 추후 웹앱 홈 화면 추가를 위한 앱 아이콘도 고려한다.
- 브랜드 레드 `#F44D52`와 화이트 중심, 단색 또는 2색 이내. 알록달록한 그라데이션·그림자·여러 색 혼합·복잡한 일러스트를 쓰지 않는다. 다른 서비스 아이콘을 복제하지 않는다.
- **워드마크(`일갈피.`)와 파비콘/앱 아이콘은 역할이 다르다.** 작은 아이콘에 워드마크 전체를 넣지 않고, 한 글자 또는 단순한 기하학적 요소를 사용한다.
- 임시 방향: 브랜드 레드 배경 + 흰 심볼(단순한 한글 `일` 또는 최소한의 형태). 작은 크기에서도 식별 가능해야 한다. **완료 스탬프의 별을 브랜드 아이콘으로 자동 전용하지 않는다.**
- 구현 시 확인할 자산(실제 존재하는 것만): `app/favicon.ico`, `app/icon.*`, `app/apple-icon.*`, `public/` 아이콘, 웹앱 매니페스트의 아이콘, `app/layout.tsx`의 `metadata.icons`. 브라우저와 웹앱에 서로 다른 이전 아이콘이 남지 않도록 한다.
- 이번 단계에서는 정책과 체크리스트만 기록한다. 아이콘 제작·파일 교체·metadata 수정은 구현 단계에서 진행한다. 최종 심볼은 시안 비교 후 확정한다.

## 16. 보안·배포 정책

- `.env.local` 및 API 키를 Git에 올리지 않는다. `.gitignore`에서 `.env*`는 제외하고 `.env.example`만 허용한다.
- Gemini API 키는 서버 환경변수(`GEMINI_API_KEY`)로만 사용하고 클라이언트에 노출하지 않는다(`NEXT_PUBLIC_` 접두사 금지). 인증/DB 비밀키도 서버 환경변수.
- 지원 여부를 확인하지 않은 Gemini 모델명을 임의로 사용하지 않는다(`GEMINI_MODEL` 환경변수, 기본값은 §7.4의 진단으로 검증).
- 코드 수정 후에는 실제 빌드·테스트·API 동작을 검증한다. 검증 전 자동 배포 금지.
- 기존 Vercel 프로젝트와 GitHub 저장소를 임의로 변경하거나 새로 만들지 않는다.

## 19. 미확정·확인 필요 항목

사용자 확인 전에는 임의로 확정하지 않는다.

1. **추천 결과 재진입**: 기존 추천이 있을 때 결과 화면으로 돌아가는 진입점(예: `추천 결과 보기`)과, 재방문 시 기본 노출 화면(목록 vs 결과).
2. **fallback 안내 방식**: 자동으로 조건 기반 추천으로 전환할 때의 안내 문구, `다시 시도` 제공 방식.
3. **3순위 추가 강조**: 점수 차이를 어떻게 정의할지. 현재 추천 결과에는 점수가 없고 AI가 점수를 만들 수 없다. 규칙 기반 점수를 쓸지, 이 강조를 폐기할지 결정 필요.
4. **로그인 선택 화면**: 인증 구현 전에 노출할지(제안: 생략).
5. **기존 프로젝트의 UI 노출**: 신규 생성 UI는 없는 상태에서, 기존 프로젝트 소속 표기·`프로젝트별 우선순위` 접기 영역을 유지할지.
6. **`완료한 일` 집계 기준**: 계획일 기준(현재 모든 통계와 일치) vs 실제 완료일 기준. 제안: 계획일 기준.
7. **지난 실행 기록 대상**: 오늘 이전 날짜만, 할 일이 있는 날짜만, 또는 미래 계획일 포함 여부.
8. **온보딩 비주얼**: v2.1의 연한 코랄 그라데이션 영역을 유지할지(이번 요청의 "과한 그라데이션 지양"과 정도 차이 확인).
9. **의견 보내기 전송 경로**: 이메일/폼/DB 중 선택, 이메일 수집 시 개인정보 안내.
10. 2순위 원 색상값, 완료 항목 원 색상, 내 기록 탭 아이콘, 칩의 상하 패딩·터치 영역 확보 방식.
11. 그래프의 미래 기간 이동 허용 여부, 0% 막대와 기록 없음의 시각 표현, 기록 없을 때 평균 완료율 표시 형태.
12. 전체보기를 URL 라우트로 구현할지 앱 내부 뷰로 구현할지.
13. 브랜드 컬러 최종값, 앱 아이콘 최종 심볼, 온보딩 최종 일러스트, 인증/DB 제공자.

### 구현 우선순위와 선행 의존성

1. **체크포인트·검증 기준선**(M0): 커밋 결정(사용자), 현재 lint/build/test 상태.
2. **작업 가능 시간 프리셋·`1시간 이내` 의미 정렬**: 의존 없음. 프롬프트·기본 추천·테스트와 함께.
3. **추천 이유 개선 + 자동 fallback + 결과 화면 전환**: §19-1·2 확인 후. 결과 화면 전환은 UI 구조 변경이므로 순위 원 색상(§19-3·10)과 함께.
4. **통계 계산 모듈**(평균 완료율·주차 분할) → **내 기록 화면·그래프·툴팁** → **전체보기 페이지**(`App` 상태 구조 변경 포함, §19-6·7·12).
5. **Empty state 공통 컴포넌트** → 홈·내 기록·추천·기간에 적용.
6. **온보딩 4장**(§19-8), **파비콘·임시 아이콘**(시안 확인).
7. **의견 보내기**: 전송 경로 결정 후. **로그인·Mixpanel·추천 평가**: P2, 외부 서비스 결정 후.

## 21. 구현 시 작업 지침

1. 새 프로젝트를 만들지 말고 기존 프로젝트를 수정한다. 사용자 데이터·완료 기록을 삭제하거나 초기화하지 않는다.
2. `AGENTS.md`에 따라 이 프로젝트의 Next.js는 학습 데이터와 다를 수 있으므로, 라우트·metadata·아이콘 관련 코드를 쓰기 전에 `node_modules/next/dist/docs/`의 해당 문서를 먼저 읽는다.
3. 한 번에 전체를 교체하지 않고 §17의 단계 순서로 진행하며, 단계마다 lint/build/test를 실행한다.
4. 작동하지 않는 기능을 작동하는 것처럼 보이게 하지 않는다(로그인, 의견 보내기, 드래그 핸들 등). 가짜 데이터·가짜 AI 결과를 만들지 않는다.
5. 완료 보고에 변경 파일, 실행 방법, 직접 테스트할 항목, 남은 작업, 실제 Gemini 호출 성공 여부, 배포 여부를 포함한다.
6. 디자인 참고용 HTML·이미지는 구현 요청 시 사용자가 제공한다. 제공되기 전까지 세부 도안을 추측해 확정하지 않는다.
