## 0. 클로드 구현 시 최우선 원칙

1. **새 프로젝트를 만들지 말고 기존 프로젝트를 수정**한다. 소스·의존성·API·로컬 데이터 구조를 먼저 확인한다.
2. 이 v2 문서는 **제품 동작과 UI 정책의 상위 기준**이다. v1에만 있는 API 검증/에러/성능/보안 세부 정책은 충돌하지 않는 한 그대로 유지한다. 바뀐 항목만 안전하게 마이그레이션한다.
3. 현재 프로젝트 경로 외의 형제 프로젝트 폴더를 읽거나 수정하지 않는다. 기존 `PRD.md`를 바꿀 때는 `PRD.v1.backup.md` 등으로 백업한 뒤 반영한다.
4. **화면만 그리는 프로토타입이 아니라 실제 입력·저장·분석·완료가 되는 웹서비스**를 구현한다. 추천 결과를 하드코딩하거나 가상의 추천을 AI 분석인 것처럼 표시하지 않는다.
5. 사용자 데이터·기존 완료 기록은 삭제하지 않는다. localStorage 스키마 변경 시 마이그레이션과 실패 시 안전한 복구를 준비한다.
6. **P0 기능을 실제로 구현한 뒤 P1 디자인 폴리싱으로 이동**한다. 추가 기능을 임의로 늘리지 않는다.
7. 변경 전 `git status`, 앱 구조, 현재 실행되는 기능, API 키 설정을 점검한다. `.env.local`/API 키는 Git에 포함하지 않는다.
8. Gemini API 연결은 **반드시 실제 호출 성공을 확인**한다. 성공하지 못했으면 AI 추천 완료로 보고하지 않는다. 규칙 기반 추천은 별도 표기한다.

## 1. 제품 정의와 핵심 UX

### 1.1 정의

- 서비스명: **일갈피**. 브랜드 표기는 **텍스트 워드마크 우선**. 별도 로고/앱 아이콘 제작은 이번 핵심 MVP의 선결 조건 아님.
- 한 줄 설명: 여러 프로젝트와 개인 할 일을 한꺼번에 비교해 **지금 무엇부터 시작할지** 판단을 돕는 우선순위 플래너.
- 사용자 가치: 일을 기록하는 것 자체보다 **판단에 드는 시간을 줄이고 실행으로 연결**하는 경험.
- 분석 핵심 기준은 세 가지: **마감 시점(날짜·선택적 시간), 중요도, 예상 소요시간**. `오늘 남은 작업 가능 시간`은 추가 우선순위 기준이 아니라 **오늘 추천 묶음의 제약 조건**이다.
- 단순 마감순 정렬이나 짧은 일 몰아주기가 아닌 **통합 비교 + 납득할 수 있는 짧고 구체적인 이유** 제공.

### 1.2 핵심 사용자 흐름

`첫 방문 온보딩(건너뛰기 가능)` → `주간 달력/선택 날짜 확인` → `할 일 빠른 입력` → `작업별 조건 아코디언 설정` → `오늘 남은 작업 가능 시간 설정` → **`우선순위 추천받기` 버튼** → `추천 순서·추천 이유 확인` → `완료 체크` → `달력 진행률 및 100% 완료 도장 반영` → `필요할 때 재추천`.

날짜 탐색(다른 날의 할 일 보기), 프로젝트 정리, 월간 기록 확인도 지원한다. **온보딩에 나온 예시 데이터가 실제 사용자의 할 일 목록에 자동 등록되면 안 된다.**

### 1.3 이번 버전 우선순위

| 구분 | 반드시 구현/검증할 내용 |
|---|---|
| **P0 — 핵심** | 모바일 기반 레이아웃, 주간 달력·날짜 전환, 할 일 등록·수정·삭제·완료, 중요도·시간·마감 조건 설정 아코디언, 마감 시각 선택 시트, 할 일 저장(localStorage), Gemini 우선순위 추천 및 상세 이유, 추천 결과 리스트, 가용 시간에 맞는 실행 추천, 날짜별 `n/m` 진행률과 100% 스탬프, 오류·빈 상태, 기존 데이터 마이그레이션, 실 API 연동·빌드 확인 |
| **P0 — 최소 소개** | 스와이프 가능한 3장 온보딩(예시 UI 크롭/간단한 미니 UI), 건너뛰기, 인디케이터 및 시작하기 버튼. 이미지 에셋 확정 전에는 CSS 기반 미니 UI를 사용하되 **실제 화면 구조와 일치**할 것 |
| **P1 — 후순위 개선** | 스탬프 아이콘 완성도/모션, 브랜딩 로고·아이콘, 온보딩 이미지 Figma 교체, 미세한 트랜지션, 스크롤/키보드 UX 세부 폴리싱, 완료 축하 메시지, 정성 사용자 테스트 반영 |
| **P2 — 이번에 제외** | OCR, 캡처/파일 파싱, 자연어 브레인덤프 AI 분리, 로그인/DB/기기간 동기화, 푸시 알림, 스트릭·경험치·레벨, 자동 시간대별 일정 배치, 복잡한 프로젝트 의존성/간트, 고급 통계/분석 연동 |

## 2. 화면 구성(모바일 중심, 데스크톱에서도 모바일 폭 유지)

### 2.1 라우트/뷰

**핵심 화면은 3개**로 본다. 추가 조작은 별도 페이지가 아니라 UI 상태/시트로 구현한다.

1. **온보딩**: 첫 방문 시 3장 슬라이드 (별도 경로 `/onboarding` 또는 루트 오버레이 중 기존 코드에 적합한 방식).
2. **홈(실행)**: 주간 캘린더, 당일 기록·진행률, 할 일 입력/수정, 조건 설정, `우선순위 추천받기`, 추천된 실행 순서.
3. **전체 할 일/프로젝트**: 날짜·프로젝트에 얽매이지 않은 할 일 조회, 프로젝트 추가·수정·삭제·작업 연결. 기존 v1 프로젝트 로직이 있다면 삭제하지 않고 이 뷰로 노출.

**홈의 월간 달력은 보기 모드**이며 별도 라우트를 필수로 만들지 않는다. **조건 아코디언 / 날짜 피커 / 시각 피커 / 추천 결과**는 별도 페이지 수에 포함하지 않는다.

### 2.2 디바이스

- 모바일 웹을 기본으로 **폭 375~430px**의 실제 사용 경험을 우선 검증한다.
- 데스크톱에서도 이전 레퍼런스처럼 가운데 **최대 430~480px 모바일형 콘텐츠 캔버스**를 보여주고 양옆은 차분한 뉴트럴 배경으로 둔다.
- 데스크톱 2단 대시보드로 다시 늘리지 않는다. 별도의 PC 최적화 레이아웃은 P2.
- 사용자는 PC에서 마우스 클릭/키보드 입력 가능해야 하고 모바일에서는 터치·스와이프 가능해야 한다. 브라우저 가로 스크롤이 없어야 한다.
- iPhone 스타일 스테이터스바/목업은 **포트폴리오용 이미지/온보딩 묘사에서만 필요**하다. 실제 모바일 웹에 가짜 운영체제 상태바를 추가하지 않는다.

## 3. 홈 화면 세부 명세

### 3.1 상단 헤더

- 텍스트 워드마크 `일갈피.` (마침표는 브랜드 시각 요소, 편집 가능).
- 서브카피 예: `복잡한 하루 속, 지금 해야 할 일부터`.
- AI 서비스라는 문구를 모든 제목에 반복해서 붙이지 않는다. 기술 이름보다 **사용자 행동/결과**를 강조한다.

### 3.2 주간/월간 캘린더

- 상단 `2026년 10월` 같은 연월 제목, 이전/다음 주 이동, `[주간 | 월간]` 세그먼트.
- **주간 기본값**: 월~일 7칸 한 줄, 요일 / 날짜 / 날짜별 `완료 수/등록 수` 또는 완료 도장.
- 기본 선택 날짜는 사용자 로컬의 `오늘`. 날짜 탭 시 **선택한 날짜의 할 일**을 아래에 표시한다. 선택과 오늘은 구별한다.
- 선택 날짜는 **숫자만 진한 레드 원형 배경 + 흰 글자**를 우선 적용한다. 요일·날짜·진행률을 세로로 전부 면으로 감싸는 긴 카드 형태는 사용하지 않는다. 오늘인데 다른 날짜를 선택했으면 오늘은 작은 점/얇은 표시, 선택일은 원형 포커스로 구분한다.
- 나머지 요일·날짜는 뉴트럴 텍스트. 진행률/스탬프는 **원형 강조와 떨어진 아래 행**에 배치한다. 칸마다 외곽 테두리 카드 7개를 반복하지 않는다.
- 해당 날짜에 계획된 작업이 있으면 `2/4`, `0/3`처럼 표시한다. **모두 완료한 날짜에는 숫자 대신 채워진 심플한 스탬프(fill형)**를 표시한다. 아이콘 확정 전 임시 사용은 가능하나 토끼/표정/복잡한 캐릭터는 사용하지 않는다.
- 등록된 할 일이 **0개인 날짜**는 `—` 또는 공백. `0/0`을 100%로 간주해 도장을 주지 않는다.
- MVP 스탬프는 **단순 기본 도장 실루엣 + 내부 체크** 정도의 작은 fill 아이콘. 마크의 라인 버전, 이모지, 표정형 성취도는 채택하지 않는다. 추후 커스텀 수정 가능하도록 컴포넌트로 분리.
- **월간**: 해당 월 전체 날짜 그리드를 보여주고 동일한 `n/m` 및 스탬프 규칙을 적용. 날짜 선택 시 홈의 날짜별 할 일 목록에 반영. 원형 진행 링(차트)은 이번 MVP에서 구현하지 않는다.
- 날짜가 바뀔 때 스탬프/완료율은 해당 날짜의 **실제 저장된 목록과 완료값에서 재계산**한다. 시각적 가짜 데이터/하드코딩 금지.
- 주간 좌우 스와이프는 이전/다음 주 이동. 월간 화면도 이전/다음 월 이동. 탭/버튼과 스와이프 모두 지원하면 좋지만, 터치 오인·충돌을 막기 위해 좌우 스와이프 영역은 **달력 내**로 제한한다.

### 3.3 날짜별 실행 기록

- 섹션 제목은 `10월 20일의 할 일` 또는 `오늘의 실행 기록` 중 선택 날짜 상태에 맞게 명확히 표시. **오늘이 아닌 날짜를 선택했는데 ‘오늘’이라고 쓰면 안 된다.**
- `완료 2/4` 및 필요하면 얇은 진행 바로 성취를 보여준다(달력 `2/4`와 같은 원본 데이터).
- **완료율 = selectedDate에 계획된 작업 중 완료 수 ÷ 해당 날짜의 계획 작업 수**. 작업 0개면 0%가 아니라 기록 없음.
- `100%` 완료 시 짧은 긍정 메시지와 달력 스탬프. 과도한 게임화·벌점·연속 기록 압박은 제외.
- **캘린더 일자별 계획과 '마감일'은 다른 값**이다. 할 일을 어떤 날짜에 추가했는지(`plannedDate`)와 언제까지 끝내야 하는지(`dueDate`, `dueTime`)를 혼동하지 않는다.

### 3.4 할 일 빠른 입력

- 제목 `할 일 입력` 또는 `오늘 할 일 정리하기`.
- 단일 텍스트 필드의 placeholder 예 `예: 포트폴리오 수정하기`. `[추가하기]` 명확한 CTA. Enter 입력 지원.
- 입력 시 선택된 날짜의 계획 목록에 등록한다. 기본 조건은 **중요도 보통 / 시간 미정 / 마감 없음**. v1의 ‘30분 필수 입력’을 강제하지 않는다.
- 별도 프로젝트 선택은 등록 후 조건 설정에서 지정할 수 있도록 하여 첫 등록의 진입장벽을 낮춘다.
- 미완료/완료 작업 모두 저장하고 표시한다. 삭제에는 확인 절차, 완료 체크는 취소 가능.
- 등록 후 작업은 **카드마다 테두리로 감싸지 않고 구분선이 있는 리스트**로 보여준다.
- 작업 순서는 일반 입력 목록에서는 등록순 유지, 추천을 받으면 **추천 결과 리스트에서만** 자동 우선순위 정렬한다. 드래그 핸들은 필요 시 디자인 요소가 아니라 실제 동작하게 만들거나 P1로 미룬다. 작동하지 않는 드래그 핸들은 표시 금지.

### 3.5 작업 리스트와 조건 아코디언

기본 행: `[완료 체크] [할 일 제목] [삭제/더보기]` 다음 줄에 연그레이 **조건 칩** (`높음`, `30분`, `내일 오후 6시`), 그 아래 `조건 설정 ▾`.

- 리스트 아이템 사이에는 얇은 디바이더 사용. 카드/박스 남발 금지.
- **조건 설정/조건 닫기**는 해당 항목의 인라인 아코디언. 한 번에 한 개를 열어도 되고 여러 개를 열어도 무방하나 동작을 일관되게 유지한다.
- 아코디언 패널은 연그레이 바탕, 중요도 / 예상 소요시간 / 마감일 / (선택) 마감시각 / (선택) 프로젝트 영역 구성.
- **조건 칩**: 연그레이 배경 `#F1F2F4` 전후, 중립 텍스트, pill `border-radius: 999px`. 상하 패딩 **4px** 유지, 좌우 패딩은 기존보다 약간 여유 있게 **약 12px** 전후. 칩 사이 gap은 기존과 유사하게 6~8px. 텍스트 한 줄 유지.
- **선택 옵션 칩**(예: `높음`, `30분`, `1시간`): `border-radius:999px`, 비선택 화이트/얇은 회색 선, **선택 상태는 진한 차콜/블랙 배경 + 흰색 텍스트**. 메인 레드 CTA와 의미를 구분한다.
- 예상 소요시간: `15분 / 30분 / 1시간 / 2시간 / 미정` 5종을 한 줄에 안정적으로 배치. 별도 `직접 입력` 링크에서 15~480분을 정확히 입력. **마지막 칩 하나가 2행에 떨어지지 않도록** 실제 375px 폭에서 검증. (`2시간 초과`는 구체 시간이 필요한 범위이므로 직접 입력으로 처리.)
- 정확도가 필요하면 `직접 입력`을 허용한다. 디자인상 단일 행이 어렵다면 균형 잡힌 두 줄로 배열한다. **옵션 수를 줄이기 위해 의미가 다른 15분과 30분을 무분별하게 합치지 않는다.**
- 설정 완료 시 즉시 리스트의 칩을 업데이트하고 저장한다.

### 3.6 추천 CTA 위치

- **할 일 입력/목록 아래에 `우선순위 추천받기` 버튼**을 배치. 제목만 있거나 자동으로 결과가 뜨지 않게 한다.
- 등록된 미완료 항목이 없으면 CTA 비활성 + `먼저 할 일을 추가해 주세요` 안내.
- 추천받기 직전 **`오늘 남은 작업 가능 시간`** 프리셋 또는 설정 컨트롤 노출. 기존 값 120분은 유지 가능. 현재 선택한 달력 날짜와 상관없이 AI 판단 기준의 `오늘`은 **사용자 실제 오늘 날짜**를 의미한다.
- **과거/미래 날짜 선택 중이면** 추천 UI에는 `추천은 오늘을 기준으로 계산해요` 설명을 표시하고 CTA를 누르면 오늘 날짜로 이동/전환한 후 추천 흐름을 시작한다. 선택된 미래 날짜를 AI의 '오늘'로 착각해 분석하지 않는다.
- 분석 로딩 시 중복 클릭 방지, API 오류 시 `다시 시도` + `기본 추천 보기` 제공.
- 작은 고지: `추천 시 할 일과 조건이 Google Gemini로 전송됩니다.` (실제 외부 API 호출 사용 시).

## 4. 추천 결과 화면(홈 하단, 핵심 기능)

### 4.1 타이틀·리스트 구조

- 섹션 제목 **`오늘의 우선순위`** (기본 권장). `오늘의 AI 실행 계획`처럼 기술명을 제목에 과도하게 쓰지 않는다.
- 타이틀 보조 설명: `마감과 중요도, 소요시간을 비교해 순서를 정리했어요.`
- 추천 완료 뒤 **숫자 순위는 원형 컬러 배경(메인 레드) + 흰 숫자**로 표시. 첫 번째를 시각적으로 더 강조할 수 있으나 과도한 1위 카드화는 금지.
- **리스트형**: `[1] 지원서 제출 [완료 체크]` / 아래 `중요도 높음` `30분` `내일 오후 6시` 등의 연회색 pill / 그 아래 한 줄 추천 이유(서브텍스트), 항목 간 얇은 구분선.
- 문장 유형: `단순히 마감이 가깝다`가 아니라 **선택된 다른 할 일 대비 실제 조건 차이**를 설명. 예: `내일 오후 6시 마감이고 30분이면 마칠 수 있어, 장시간 작업 전에 처리하는 편이 좋아요.` 또는 `마감은 금요일이지만 2시간 넘게 걸리는 중요한 작업이라 오늘 일찍 착수할 필요가 있어요.`
- LLM이 존재하지 않는 기한/조건/다른 작업 비교를 창작하지 않도록 입력 기반 사실만 사용.
- 완료 체크는 추천 리스트, 입력 목록, 달력 기록에 실시간 동기화. 완료 시 기존 순위에서 사라지지 않고 체크/취소선으로 남아 실행 내역을 보여준다.

### 4.2 오늘의 실행 묶음(Focus)

- 전체 순위(모든 미완료 작업 비교)와 별개로, 가용 시간에 맞춰 **최대 3개**를 `지금 시작할 일` 또는 `오늘 먼저 할 일`로 제안.
- `추천한 순서`, `각 예상 시간`, `합계 / 남은 가능 시간`, `추천 이유`, `n/m 완료` 표시.
- **가용 시간보다 큰 작업은 전체 순위에서 제외하지 않음**. Focus에 들어갈 수 없으면 사유/주의사항으로 안내.
- 완료 체크만으로 매번 재추천을 강요하지 않는다. 새 작업 추가·조건 변경·가용 시간 변경·날짜 변경 시 `다시 추천받기` 유도.
- 추천 순서가 사용자의 실행을 **강제하지 않는다**. 중간 항목 먼저 완료해도 정상 처리하며 달성 보상을 깎지 않는다.

### 4.3 프로젝트 비교(기존 v1 기능 유지)

- 프로젝트를 1개 이상 등록했다면 기존 v1의 `프로젝트별 우선순위`와 `전체 작업 순위` 분석을 **삭제하지 않는다**.
- 핵심 UX의 `오늘의 우선순위` 결과를 우선 노출하고, `프로젝트별`/`전체 순위` 상세는 **접기/탭/더 보기**로 제공해 모바일 스크롤 길이를 줄인다.
- 프로젝트 소속 작업과 개별 작업을 **모두** 전체 분석에 포함한다. 프로젝트 순위와 작업 순위의 이유가 상충하지 않도록 v1 검증 정책 유지.
- 결과 타입에 따라 `AI 분석` / `기본 추천(규칙 기반)`을 **정직하게 구분**하되 타이틀에 `AI`를 남발하지 않는다.

## 5. 날짜·마감 UI 정책(중요: 모호함 해결)

### 5.1 두 날짜의 차이

| 필드 | 의미 | 사용처 |
|---|---|---|
| `plannedDate` | 사용자가 **그날 하려고 등록한 날** | 캘린더 `2/4`, 날짜별 목록, 완수 도장 |
| `dueDate` | 작업을 **마쳐야 하는 마지막 날짜**(선택) | 우선순위 판단, 조건 칩 |
| `dueTime` | 마감 날짜에 붙는 **정확한 시각**(선택) | 시각 임박 우선순위, 조건 칩 |
| `completedAt` | 실제 완료 버튼을 누른 시각 | 완료 상태 복원·날짜 기록 확장용 |

**예:** 10/20에 `지원서 작성`을 계획하고 10/21 오후 6시 마감으로 설정하면, 작업은 **10/20 목록**에 보이고 칩에는 **`내일 오후 6시`**가 보인다. `dueDate`를 바꿔도 캘린더의 `plannedDate`는 자동으로 이동하지 않는다.

### 5.2 짧은 마감 칩 표기 — 날짜를 모호하게 숨기지 말 것

| 상황 | 표시 예시 |
|---|---|
| 마감 오늘(시각 없음) | `오늘` |
| 마감 오늘 18:00 | `오늘 오후 6시` |
| 마감 내일 | `내일` |
| 마감 내일 12:00 | `내일 낮 12시` |
| 오늘·내일 이후 **이번 주 안** | `수요일` / `금요일 오후 6시` |
| 다음 주 | `다음 주 화요일` / `다음 주 화요일 오후 3시` |
| 더 먼 날짜(예: 2주 이상) | `11월 6일` / `11월 6일 오후 3시` |
| 이미 지남 | `마감 지남` (필요하면 상세에서 절대 날짜) |
| 마감 없음 | 조건 칩 자체를 생략하거나 설정 화면에서 `마감 없음` |

- **월/일/연도 전체 숫자를 칩마다 강제로 나열하지 않는다**. `10/21 18:00` 형태 대신 날짜와 시각의 상대적 표현을 우선 사용.
- **상세 편집 패널에는 실제 `YYYY.MM.DD` 값을 정확히 보여줘** `다음 주 수요일`처럼 짧게 표시한 칩과 실제 저장 날짜 사이 혼란 방지.
- `오전 12시=자정`, `낮 12시=정오`. 24시간제의 00:00/12:00을 내부 저장 값으로 사용. 12시 표기는 `자정 12시`/`낮 12시`로 오독을 막는다.
- 기존 v1의 `D-3`, `오늘 마감`, `10/21` 혼재 방식은 이 규칙으로 교체.

### 5.3 마감 날짜와 시간 선택

- **마감일(선택)**: 기본 날짜 선택기(모바일 캘린더 UI 또는 성능 좋은 기존 컴포넌트). 과거 날짜 저장도 가능하나 안내 노출.
- **마감시각(선택)**: 날짜가 있을 때 활성화. 탭하면 모바일 **바텀시트**를 연다.
- 바텀시트 타이틀 `마감 시각 선택` / 도움말 `정확한 마감 시각이 있을 때만 설정하세요.`
- **빠른 선택 칩 제거**. `오전·오후 / 시 / 분`의 3열 스크롤(휠) 또는 안정적인 리스트형 선택 컨트롤. 옵션을 둥근 작은 팝오버 3개로 띄워서 선택하기 어려운 UI는 사용하지 않는다.
- 아래 `[시간 없음]` `[적용하기]`(레드 CTA). 배경 탭/닫기, 시트 내 스크롤, 키보드·접근성 고려.
- 취소 시 기존 설정 유지, 적용 시 `dueTime`에 `HH:mm` 24시간제 값 저장. 마감 날짜 없이 시각만 남을 수 없음.
- 단계가 지나치게 무거우면 P0에선 시스템 기본 `input[type=time]`을 예쁘게 감싼 방식도 허용. **정확히 작동하는 경험이 시각적 휠 시뮬레이션보다 우선**.

## 6. 입력 값 정책 / 저장 스키마 변경

### 6.1 작업 입력 기본값

| 필드 | 조건 | 기본값 및 규칙 |
|---|---|---|
| `title` | 필수 | trim 1~100자 |
| `plannedDate` | 필수 | 등록 시 선택 중인 날짜, 사용자 로컬 `YYYY-MM-DD` |
| `projectId` | 선택 | `null`; 프로젝트 기능은 v1 유지 |
| `importance` | 선택(3종) | `medium`(`보통`) |
| `estimatedMinutes` | 선택 | `null`(`미정`); 30분/1시간/2시간/2시간 초과 등 UI와 정확한 숫자 저장 정책을 일치시킬 것 |
| `dueDate` | 선택 | `null`, 로컬 `YYYY-MM-DD` |
| `dueTime` | 선택 | `null` 또는 `HH:mm`, `dueDate` 없이 사용 불가 |
| `isCompleted` | 시스템 | `false` |
| `completedAt` | 시스템 | 완료 시 ISO, 완료 취소 시 `null` |

#### 예상 시간 **미정/범위** 처리에 관한 설계 결정

UI의 `2시간 초과`, `30분 이내`는 정확한 숫자가 아니므로 **MVP AI 계산에 임의의 정확한 값으로 속여 넣으면 안 된다**. 다음 구현 정책을 권장한다.

- **확정 정책: `15분 / 30분 / 1시간 / 2시간 / 미정` 5종 + 별도 `직접 입력`(정수 15~480분).** 범위 표현 `30분 이내`, `2시간 초과`를 정확한 수치로 임의 환산하지 않는다.
- `estimatedMinutes=null`인 작업도 저장하고 **AI 및 기본 추천의 전체 우선순위 대상**에 포함한다. 단 **시간을 합산할 수 없으므로 Focus 시간 예산 대상에서만 제외**하며 `예상 시간을 설정하면 오늘 실행 추천에도 포함할 수 있어요` 안내. `/api/recommend` 입력 검증은 `null | integer(15..480)`, Gemini 입력도 `null` 허용, 결과 검증은 Focus에 `null` 작업이 있으면 실패하도록 수정한다. 기본 추천은 `null`을 이유 없이 최하위 고정하지 않고 중요도·마감으로 순위를 판단한다.
- 가용 시간에 넣을 수 있는 **예상 시간이 확정된 작업이 하나도 없으면** Focus는 빈 배열과 구체적 안내를 반환한다. v1의 최소 1개 Focus 검증은 `estimatedMinutes !== null && estimatedMinutes <= availableMinutes`인 작업이 하나라도 있을 때에만 적용한다.
- v1의 모든 기존 숫자형 소요시간은 마이그레이션 후 그대로 유지한다. `미정`을 0분이나 30분으로 저장하지 말 것.

### 6.2 저장·마이그레이션

- 원본 스키마는 `ilgalpi:v1`에 `projects`, `tasks`, `preferences`, `recommendation`을 저장한 상태. **기존 사용자가 등록한 데이터가 있다면 지우거나 초기화하지 않는다**.
- 신규 `ilgalpi:v2` 또는 버전 명시 스키마를 추가하고 첫 실행 시 v1 → v2 **단 한 번 안전하게 복사/변환**한다. 저장 완료 검증 전 v1 키를 삭제하지 않는다.
- 레거시 미완료 작업의 `plannedDate` 기본값은 **마이그레이션 당일(로컬 오늘)**로 채워 사용자가 잃어버리지 않게 한다. 기존 완료 작업은 `completedAt` 로컬 날짜가 유효하면 그 날짜, 없으면 `createdAt` 유효 날짜, 둘 다 없으면 마이그레이션 당일로 배치(사용자에게 과거 분류가 추정값일 수 있음을 안내).
- 기존 `dueDate` 유지, `dueTime=null`, 숫자형 `estimatedMinutes` 유지, `completedAt`은 기존 값 유지. 기존 추천 스냅샷은 필드 변화에 따라 invalid/stale로 표시하고 재추천을 유도.
- 레거시/신규 데이터의 plannedDate 이동은 사용자가 명시적으로 날짜를 바꿀 때만 수행.
- 날짜별 `completed/total` 및 스탬프는 **저장된 작업에서 매번 계산**하며 별도의 독립적인 수치를 저장하지 않는다(서로 어긋나지 않게).
- 작업을 늦게 완료했다면 일갈피의 이번 MVP 달력은 **원래 계획한 날짜의 작업 완료 상태**를 반영한다. *완료한 실제 날짜에 별도 작업 기록을 복제하지 않는다.* 이후 실제 수행일 기준 분석은 V2 후보.
- API 키는 서버 환경변수로만 보관, `.env.local` gitignore 유지.

## 7. 추천 엔진·API 변경 범위

### 7.1 보존 항목(v1 §7, §8)

아래는 **원칙적으로 v1 그대로 유지**: `/api/recommend`, Gemini 서버 호출, 환경변수, UUID → 축약 ID 매핑, API 응답 구조(`projectRankings`, `taskRankings`, `focusPlan`, `warnings`), 순위/ID 유효성 검증, Focus 3개 이하, Focus 예상 시간 합 ≤ 가용 시간, 구조화 출력 검증 후 최대 1회 재시도, 타임아웃·오류 처리, 규칙 기반 기본 추천, AI와 기본 추천 구분, 로컬 타임존/날짜 기반 판단, 신규/수정 시 stale 판정, 완료만 했을 때 stale 없음.

### 7.2 변경해야 하는 입력

- 서버가 **`dueTime`** 을 받아 날짜만 있는 작업과 정확한 시간 마감이 있는 작업을 구별하도록 요청/검증/프롬프트 변경.
- 시각이 있는 오늘 마감은 당일 09:00 vs 18:00 등 남은 시간을 판단할 수 있어야 한다. **사용자 로컬 시각과 시간대**를 사용하고 서버 로컬/UTC를 혼동하지 않는다.
- `plannedDate`는 **일별 달력 분류용**이며 마감의 대용으로 삼지 않는다. 이 필드는 AI 분석에서 꼭 필요한 경우가 아니면 우선순위 점수에 별도 가중하지 않는다.
- 중요도·마감·예상 시간 외 피로도, 장소, 감정 등 추가 가중치 금지.
- 추천 사유의 **quality rule**: `높음/30분/내일`을 단순 반복하지 말고, 어떤 *조건 조합 또는 다른 작업과의 차이* 때문에 이 순서인지 한 문장으로 설명. **근거 없는 점수·가정·일정 생성은 금지.** 비교 근거가 약하면 과도한 이유를 지어내지 말고 사실 위주로 간결히 표기.
- 오늘 남은 가능 시간을 정하지 않았다면 기존 120분 기본값 사용 가능하지만, 사용자에게 눈에 보이는 값과 정확히 일치해야 한다.
- `estimatedMinutes=null` 관련 정책은 §6.1 확정 정책을 따라 서버 검증/Focus 생성/기본 추천 양쪽에서 동일하게 처리한다.

### 7.3 상태 정책

- 새 작업 등록/삭제, 제목·프로젝트·마감·마감시각·중요도·예상시간 변경, 가용 시간 변경, 실제 날짜 변경 → 기존 추천 `재추천 필요`.
- 완료/완료 취소만으로 추천 무효화하지 않는다. 체크·완료율은 즉시 반영.
- 추천 대상에는 프로젝트 소속 여부에 관계없이 **모든 미완료 작업** 포함. 특정 날짜 필터로 전역 우선순위를 잘못 줄이지 않는다.
- Focus에서 추천받은 작업이 원래 다른 날에 계획되어 있더라도 **추천 생성 자체가 `plannedDate`를 조용히 변경하지 않는다**. 실행 우선순위와 계획 날짜는 별개.
- 작업이 30개를 넘으면 v1과 같이 AI 분석 한도를 표시하고 기본 추천으로 진행할 수 있도록 한다.

## 8. 디자인 가이드(현재 결정 사항)

### 8.1 방향

- **화이트·그레이 기반 + 선명한 코랄 레드 포인트**. 채도가 낮은 탁한 레드가 아니라 생동감 있는 레드. 기존 보라·형광 그린·당근 같은 오렌지 중심안은 사용하지 않는다.
- 예시 토큰(추후 피그마 수정 가능):
  - `--color-primary: #F44D52` (CTA·추천 순위·선택 날짜)
  - `--color-primary-soft: #FFF0F0` (필요한 일부 보조 영역)
  - `--color-text: #19191B` (주요 제목·본문)
  - `--color-text-subtle: #767780`
  - `--color-border: #E8E9ED`
  - `--color-surface: #FFFFFF`
  - `--color-surface-muted: #F6F7F8`
  - `--color-chip: #F0F1F3`
  - `--color-option-selected: #242428` (조건 옵션 선택 상태)
- 레드는 **주요 행동 CTA**, **달력 선택일의 숫자 원**, **추천 1·2·3번 숫자 원**에 우선 사용. 조건 칩, 긴 설명, 캘린더 각 날짜를 전부 강한 레드로 채우지 않는다.
- 달력 `선택 날짜`는 진한 원형. 100% 성취 **도장은 작고 분명한 fill형**(포인트 컬러 또는 중립 컬러). `2/4` 텍스트는 회색.
- 리스트 아이템: 전체 테두리 카드 반복 대신 여백과 얇은 구분선. 조건 설정 열렸을 때만 연그레이 패널 사용.
- 주요 버튼 `우선순위 추천받기`, `추가하기`, `적용하기`는 primary 레드 배경 + 화이트 텍스트. 조건 옵션 selected는 **차콜**.
- 칩 라운드 999px / 상하 패딩 4px / 좌우 12px 전후, 가로 줄바꿈 안정성 확인. 타이포 시스템 폰트 또는 프로젝트 현재 폰트 유지.
- 로고/아이콘 미확정: **`일갈피.` 텍스트 로고로 MVP 진행**. AI 마법봉과 같은 범용 아이콘을 로고로 확정하지 말 것.

### 8.2 빈 상태

- 데이터 0개: `아직 등록한 할 일이 없어요. 먼저 생각나는 일부터 적어 보세요.` + 할 일 입력 CTA.
- 선택한 날짜만 비어 있음: `이 날짜에 계획된 할 일이 없어요.` (다른 날짜/프로젝트에 등록된 작업은 숨겨도 데이터 삭제 금지).
- 추천 전: `할 일을 추가한 다음, 우선순위를 추천받아 보세요.`
- 추천 실패: 원인과 재시도, 기본 추천 버튼.
- 모든 작업 완료: 완료 상태를 유지하되 `오늘 할 일을 모두 마쳤어요` 메시지. 존재하지 않는 추천 카드를 렌더링하지 않는다.

## 9. 온보딩 3장(최소 구현)

**목적:** 서비스 내부에 예시 할 일이 없더라도 앱의 핵심 UX를 처음부터 볼 수 있게 한다. **샘플 데이터가 실제 저장소로 들어가면 안 된다.**

1. **할 일을 자유롭게 정리해요** — 할 일 입력 + 조건 칩/아코디언 UI 일부 크롭. 서브카피 `생각나는 일을 적고, 중요도와 마감·소요시간을 설정해요.`
2. **무엇부터 할지 순서를 찾아요** — `우선순위 추천` 결과 UI 크롭(번호·칩·짧은 이유). 서브카피 `마감과 중요도, 시간을 비교해 지금의 실행 순서를 제안해요.`
3. **완료한 만큼 기록해요** — 주간 캘린더 UI 크롭(`2/4`, 완수 스탬프). 서브카피 `하루의 완료 기록을 모으고, 다 마친 날에는 도장이 찍혀요.`

- 모바일 전체 화면, 큰 타이틀 + 짧은 서브카피 + **중앙에 실제 UI 구조를 활용한 크롭 이미지/미니 목업**. 장식 아이콘+글씨만 있는 슬라이드는 지양.
- 스와이프하여 앞/뒤 이동 가능. 하단 인디케이터는 현재 위치를 보여주고 **탭으로 해당 장 이동 가능**.
- 우측 상단 `건너뛰기`, 하단 `[다음]`(1~2장) / `[시작하기]`(3장). `이전` 버튼은 별도로 두지 않는다(스와이프/인디케이터로 복귀).
- 첫 진입 1회만 자동 노출. 새로고침 때 계속 뜨지 않게 로컬 상태 저장. 다시 보는 기능이 필요하면 헤더/정보 링크에서 접근 가능(P1).
- 예시 화면은 코드에 고립된 **정적 프레젠테이션 데이터**를 사용하고 앱 로컬 저장소에 섞지 않는다. 추후 Figma 이미지로 교체 가능하도록 슬라이드 컴포넌트 분리.

## 11. 이번 MVP에서 보류할 세부 디자인과 열린 이슈

1. **브랜드 심볼·앱 아이콘**: 로고가 없는 대신 `일갈피.` 워드마크 사용. 본격 브랜딩은 배포 후.
2. **스탬프 실루엣**: fill + 체크 중심 단순형으로 임시 사용. 완성형 도안/애니메이션은 P1. **얼굴 표정/레벨/토끼 캐릭터 미적용**.
3. **예상시간 미정**: null로 저장, 전체 순위 포함, Focus에서는 제외. 화면에 간단히 안내. AI와 기본 추천 양쪽에서 동일하게 처리할 것.
4. **반복되는 캘린더 캡션**: 사용자 테스트 후 완료율과 스탬프 간 중복 정보 최소화.
5. **자동 일정 재배치**: Focus 추천만으로 `plannedDate`를 변경하지 않음. 향후 '오늘 계획에 담기' 명시적 동작은 별도 검토.

## 12. 클로드 코드 작업 수행 지침(이 문서를 전달받으면)

1. 현재 소스의 주요 컴포넌트/데이터 타입/API와 v1 대비 변경점 **표로 10개 이하** 간단히 보고.
2. 전체 코드를 한 번에 대체하지 말고 **M0 → M1 → M2 → M3** 순서로 기존 파일을 수정. 각 단계에서 lint/build/test 가능하면 실행.
3. UI는 이번 대화에서 정리한 **모바일형 주간 캘린더 > 날짜별 실행 기록 > 할 일 입력·조건 > 추천 CTA > 추천 결과 리스트** 순서를 준수.
4. 실제 기능이 미완료인 버튼은 작동하는 것처럼 보이게 하지 않는다. 구현이 어려우면 보류 내용과 이유를 정확히 설명.
5. 완료 시 변경 파일 목록, 실행 방법, 직접 테스트할 5가지 포인트, 남은 작업, 실제 Gemini 호출 성공 여부, 배포 여부를 보고.
6. 원래 v1 기술 명세 중 여기 명시하지 않은 검증 규칙·프로젝트 로직·기본 추천/에러 처리를 **누락하지 말 것**.
